Protect and share

Keys and pairing

Each role creates its own post-quantum keys, locked with a passphrase, and the parties exchange public key files whose fingerprints can be compared by eye.

Where
Workspace, Keys card and Join card
Labels in the app
Create Alice's keys, Unlock Alice's keys, Exchange public keys with the cloud, Import the public keys, Passphrase
What you get
An ML-DSA key pair for Alice; ML-KEM and ML-DSA key pairs for each doctor and for the cloud; .pqpub public key files.
What the server sees
Public keys only.
Limits
A passphrase cannot be recovered. Fingerprints are only useful if compared over a path you trust.
Tested by
test_m1_core.py: test_kem_round_trip, test_signature_round_trip, test_vault_encrypts_and_checks_passphrase, test_pairing_file_round_trip

Join requests and approval

A doctor sends a signed join request; Alice sees it with the key fingerprint, ticks the groups to allow and approves, and the doctor fetches a sealed access pass.

Where
Workspace, Join card (doctor) and People and access card (Alice)
Labels in the app
Send join request, Look for new requests, Approve for the ticked groups, Fetch mailbox
What you get
An access pass (capability) with the keys of the chosen groups, sealed for that doctor with ML-KEM and AES-256-GCM and signed by Alice.
What the server sees
That a request and a sealed pass passed through, their sizes, and which groups the doctor may ask about. Not the group keys.
Limits
A doctor's groups are fixed at approval. To change them, revoke and approve a new request.
Tested by

Build the index and publish the summary

Uploading documents builds an encrypted index (one masked entry per word, linked in a hash chain), and Publish summary sends a signed, encrypted summary that doctors check every answer against.

Where
Workspace, Documents and Publish cards
Labels in the app
Publish, Publish summary, Changes are waiting. Doctors do not see them until you publish., Everything is published.
What you get
Index entries at addresses computed with HMAC-SHA3-256; a summary (state) padded, encrypted, versioned, with an expiry time, signed with ML-DSA.
What the server sees
Addresses and masked values that look random, how many entries there are, the batch size, and the time of each upload.
Limits
A summary is valid for a set time (default 24 hours). Inside that time the cloud can still show the newest summary a doctor has already seen.
Tested by
test_m2_correctness.py: test_random_workload_matches_plaintext_reference, test_unpublished_updates_are_not_visible_until_publish; test_m1_core.py: test_index_derive_matches_definition, test_hash_chain

Change and revoke

Update: add and delete with forward and backward privacy

Adding or deleting documents sends a numbered, signed batch; new entries get new addresses an old token cannot reach (forward privacy), and a delete is one more masked entry (backward privacy).

Where
Workspace, Documents and Publish cards
Labels in the app
Lock and upload a document, Delete, Publish summary
What you get
A signed update batch with a sequence number; the cloud accepts only the next number.
What the server sees
That an update happened, when, and how large it was. It removes a deleted document's box.
Limits
Backward privacy here hides which older entry a delete cancels. The cloud still sees the delete batch and drops the deleted document.
Tested by
test_m2_protocol.py: test_forward_privacy_new_updates_share_no_address_with_old_tokens, test_forged_modified_replayed_and_out_of_order_updates_are_rejected

Revoke: policy R and policy RE

Alice takes a person's access away; the cloud refuses their pass, each affected group gets a new key, and only the people who stay receive it. Quick (policy R) or Thorough (policy RE).

Where
Workspace, Revoke card
Labels in the app
Revoke, Quick (policy R), Thorough (policy RE), Take away access
What you get
A new key period (epoch) per group, sealed once per remaining doctor. With RE every document is encrypted and signed again.
What the server sees
That a revocation happened, which pass is refused, and with RE the full re-upload.
Limits
Policy R: documents from before the change stay under the old key, so a revoked person who teams up with the cloud can still read them. Policy RE closes that gap but re-encrypts everything. Cannot be undone. Known display issue: after a revocation the Stage still lists the revoked doctor's old groups and last search result.
Tested by
test_m2_revocation.py: test_revoke_policy_r, test_revoke_policy_re, test_r_then_re_then_new_member

What the server sees, in one place

It sees
encrypted documents and their sizes; how many documents and index entries exist; group names, how many doctors there are and which groups each may ask about; when each request happens and how large it is; which addresses a search asks for, so a repeated search is visible; how many entries matched; that an update or a revocation happened.
It never sees
search words; document text or titles; group keys or any private key.

Not included

Things the app does not do. Each one was checked against the code.

  • No deployment across machines: the cloud listens on 127.0.0.1 only, without TLS.pqsse/cloud/server.py refuses non-loopback binds; tests/test_m3_http.py::test_server_refuses_non_loopback_bind
  • No connection to a real cloud provider.The only server is pqsse/cloud, started as a child process.
  • No sync between devices or users' computers.Each role's data is a local SQLite file under %LOCALAPPDATA%\PQ-SSE-Desktop.
  • No more than one data owner.README Known limits: single owner.
  • No change of a doctor's groups after approval.README Known limits: no capability update.
  • Searches are one word at a time; no phrases or Boolean queries.Receiver.search takes one keyword.
  • Not audited by outside experts.README Known limits.
  • The default post-quantum code is pure Python: slow and not constant time.pqsse/pqbackend.py uses kyber-py and dilithium-py unless liboqs is importable; liboqs was never tested here.
  • Installers are not code signed.docs/DISTRIBUTION.md.
